# ADR-0001: Research-Driven Decision Workbench

## Context

项目已经具备行情缓存、结构事实、V2 状态、候选扫描、条件化交易计划和单票图表。现有界面同时使用研究、决策和执行语言，但系统没有真实账户、成交和持仓状态；现有历史统计也没有完整成交、费用、仓位和资金曲线模型。

用户当前的主要使用方式是扫描候选、打开单票、核对实时行情与图表信号，然后自行判断并在系统之外交易。用户不需要系统强制记录每次决策或手工维护真实持仓，同时希望保留未来成长为自动化交易的可能。

## Decision

项目定位为“研究驱动、人工判断优先、可演进至受限自动执行的 A 股短线个人决策工作台”。

当前阶段：

- 研究引擎负责事实、信号、候选解释和事件研究。
- 决策界面负责呈现信息和条件化计划，不替用户作最终决定。
- 不要求用户记录每次决策。
- 不要求用户录入真实持仓。
- 不接券商，不提交订单。
- 模型推演仓位与真实持仓在概念上严格分离。

未来自动化通过新增执行意图、风险闸门、订单、成交和持仓模块实现，不把现有信号字段直接扩展成订单状态。

## Consequences

正面影响：

- 当前交互保持轻量，不增加交易日志负担。
- 产品语言与实际数据能力一致。
- 研究结果和实时行情可以独立演进。
- 未来接入模拟盘或券商时，无需重写信号事实层。

需要承担的工作：

- 将“持仓”改为模型推演语义。
- 将当前“回测”改为事件研究语义。
- 为数据、策略和读模型增加可追溯身份。
- 将在线查询从文件遍历迁移到持久化索引。
- 为未来执行层保留明确边界，但不提前实现空壳功能。

## Rejected Alternatives

### Pure Research Tool

只保留历史统计和规则实验，移除候选与单票计划。该方案不符合用户日常依赖候选和实时单票研判的方式。

### Execution Assistant Now

立即要求用户维护持仓、账户和决策日志。该方案增加日常摩擦，且当前没有券商成交数据作为真实来源。

### Automatic Trading Now

直接把信号连接到订单。当前缺少真实成交模型、独立风险闸门、订单幂等、账户状态和故障恢复，不具备安全基础。

## Follow-Up Decisions

- 定义三个稳定读模型并确定 schema version 规则。
- 选择 SQLite 元数据索引结构和快照迁移方式。
- 定义交易日历、K 线状态和数据 revision。
- 用户已选择候选优先作为默认入口方向；后续验证单票直达与候选横向比较等次要任务路径，不据此提前决定前端技术栈。
