# ADR-0004: Candidate-First Default Entry

## Context

系统同时服务两种核心起点：没有预设标的时发现候选，以及已有代码时查看单票行情和信号。用户明确表示日常更常从候选池开始。当前生产页也已默认显示候选池，并在顶层提供“单股确认”入口。

## Decision

- 默认入口采用候选优先：首先呈现全市场候选和横向比较能力。
- 单票分析继续作为一级能力；从候选首页可通过顶层入口进入单票页，直接输入代码并开始分析，不得隐藏在候选详情深处。
- 本决策只确定默认工作流起点，不决定候选排序公式、具体视觉语言或前端技术栈。
- 风险观察与参与候选之间的横向核对仍是核心任务，不把候选首页变成单纯的排行榜。

## Consequences

- 后续 UI 收敛以候选列表为主要工作区，同时保留清晰的单票入口和返回候选上下文的路径。
- 在进入较大生产 UI 改造前，仍需核对“输入已知代码”和“风险票对比参与候选”任务没有明显退化，并保留加载、失败和行情新鲜度状态。
- SQLite 候选读链是否切换仍由读模型契约、排序语义及失败降级验收决定；不能由默认入口偏好替代这些技术门槛。

## Evidence And Limits

该选择来自用户明确表达的日常入口偏好，不是计时实验或跨多个真实使用时段的定量结果。它足以确定当前设计方向，但不能据此声称候选优先在所有任务上效率更高。
