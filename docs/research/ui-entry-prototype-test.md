# 首页入口原型验证

## Question

当前产品同时存在“从全市场候选发现机会”和“拿已有代码快速确认”两种高频动机。
在没有使用证据前，不继续用文档偏好决定默认首页。

## Hypotheses

- 候选优先会缩短无预设标的时的发现路径，并改善候选间横向比较。
- 单票优先会缩短已有代码时的行情与信号确认路径。
- 两者都必须保留数据身份、正式信号状态、失效条件和原候选上下文。

## Prototype Controls

两份原型共享视觉语言、样例数据、ECharts 配置和右侧事实内容，只改变页面的主任务
和空间分配。样例数字不用于评估策略质量。

## Tasks And Measures

1. 无预设标的：找到一只可继续核对的参与候选，复述入池原因和缺少确认。
2. 已知代码：输入 `300829`，指出最后 K 线状态、信号、失效条件和数据来源。
3. 风险对比：打开风险票，再切换到参与候选，说出许可差异。

记录每项任务完成时间、误点/回退次数、遗漏字段和 1-5 分把握度。至少跨三个真实
使用时段重复，而不是一次看图决定。

## Decision Rule

- 默认入口优先匹配用户明确表达的日常起点；任务走查用于发现次要路径退化，不把单次静态原型体验包装成定量胜负。
- 次要任务必须能在一次明确动作内进入，不能深藏。
- 默认入口确定后仍保留另一类任务的一步可达路径；每个工作区只承担一个主任务。
- 在结论形成前，不决定是否迁移 React/Vue；当前原型验证的是信息架构，不是技术栈。

## Limitations

当前只有静态样例，没有真实加载延迟、错误恢复、超长候选列表和移动端日常行为。
SQLite 摘要分页和单票读取模型已经具备 opt-in API；若进入生产试用，仍需接入真实
接口、补齐加载/失败/降级状态，并验证长列表和真实响应延迟。

## Initial Feedback (2026-09-24)

用户初看原型后反馈：目前没有明显找不到或看不懂的信息，但整体 UI 与页面设计仍有优化空间。
这支持保留现有信息层级、先打磨视觉表达；单凭初看不判断任务效率。已据此对静态原型做一轮视觉收敛，生产页面尚未修改。

## User Entry Preference (2026-09-24)

在被问及日常通常从何种任务开始时，用户明确选择“候选优先”。因此默认工作流方向已确定为候选优先，单票分析仍须一键可达。该证据是用户明确偏好，不是计时实验或多时段使用数据；后续走查应聚焦已知代码直达单票、风险票与参与候选对比这两条次要路径，以及整体视觉质量。
