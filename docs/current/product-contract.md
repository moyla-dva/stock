# Product Contract

## Product Definition

本项目是一个研究驱动、人工判断优先、可逐步演进到受限自动执行的 A 股短线个人决策工作台。

当前系统负责提供可靠行情、结构事实、候选、信号解释和条件化参考。用户保留最终判断权，并在系统之外完成实际交易。当前产品不要求用户记录每次决策，也不要求录入真实持仓。

## Primary Workflow

```text
候选优先首页
-> 横向查看全市场候选、许可和入池原因
-> 打开单票核对结构、信号和最新行情
-> 用户自行决定等待、放弃或执行
-> 必要时回看历史事件和策略证据
```

候选优先是用户选择的默认工作流起点，不代表排序公式或视觉设计已经定稿。当前生产页已默认打开候选池，并提供顶层“单股确认”入口；用户已有代码时无需先进入候选详情，进入单票页后即可输入代码并开始分析。风险验证、修复观察和参与候选之间的横向比较也应保留。

## System Responsibilities

系统当前负责：

- 获取和缓存行情数据，并逐步补齐可追溯的来源和 revision 身份。
- 在已具备状态元数据的路径中区分已收盘 K 线与盘中预览 K 线。
- 计算结构事实、状态、许可和条件化计划。
- 生成并解释参与候选、风险验证和修复观察结果。
- 在图表中展示历史已确认信号和当前行情。
- 保存策略自身的信号、版本和扫描快照，以支持研究与复现。

## Candidate Ranking Boundary

个股优先级依据该股自身的信号/结构、确认、风险和宏观许可。行业与概念只用于标签展示、
候选分布统计和筛选，不参与个股加分、环境许可或执行状态；板块指数行情、市场宽度和
类别分桶回放已退出当前决策链。细节与兼容字段规则见
[ADR-0002](../adr/0002-candidate-ranking-ownership.md)。

系统当前不负责：

- 代替用户作出最终买卖决定。
- 推断用户一定持有某只股票。
- 将模型推演仓位表述为真实持仓。
- 将事件后收益统计表述为可交易策略收益。
- 管理真实账户、委托、成交和资金。
- 自动向券商提交订单。

## Data Semantics

每份用户可见分析结果最终都应能够追溯到：

```text
instrument
+ as_of
+ bar_state
+ data_source
+ data_revision
+ start_key
+ strategy_version
+ rule_results
+ generated_at
```

字段语义：

- `as_of`：分析覆盖的最后一个市场时间。
- `bar_state`：`closed`、`preview` 或 `mixed`。
- `data_source`：生成主要行情序列的数据源。
- `data_revision`：能够识别输入行情内容的稳定版本或哈希。
- `start_key`：生成指标和扫描结果所使用的历史窗口起点身份。
- `strategy_version`：生成状态、信号和计划的策略版本。
- `rule_results`：可解释的事实和规则结果，不是只有最终标签。
- `generated_at`：本次结果生成时间，不等同于市场时间。

盘中行情可以作为预览叠加到图表，但不能静默覆盖已确认的收盘事实。正式信号默认基于已收盘 K 线；任何盘中预判必须具有不同状态和视觉语义。

当前单票日线已传递 `bar_state`、`data_source`、`data_revision`、`generated_at` 和日历 revision。旧缓存没有历史来源证据时，`data_source` 继续返回 `unknown` 并在 `data_quality.issues` 明示。2026 日历由沪、深、北交易所年度休市公告提供官方证据，更早历史目前仍为 provider；`bar_state` 仍只是末根日线形成状态，不是扫描或历史股票池完整性证明。

## Product Language

在尚未具备真实持仓和完整成交模型前，产品使用以下语言：

| 避免使用 | 当前推荐 | 原因 |
| --- | --- | --- |
| 空仓 | 入场研判 | 当前只是查看入场相关信号，不代表账户空仓 |
| 持仓 | 信号后跟踪 / 持仓推演 | 当前仓位来自模型假设，不是真实持仓 |
| 回测 | 历史事件统计 / 事件研究 | 当前未模拟完整成交、费用、仓位和资金曲线 |
| 回测胜率 | 事件后上涨比例 | 避免暗示可直接交易的胜率 |
| 执行建议 | 条件化计划 | 用户仍需自行判断和交易 |
| 减仓 / 卖出 | 风险条件触发 / 假设持仓动作 | 没有真实持仓时不能表述为用户动作 |

内部模块名可以分阶段迁移，但所有新 UI 和新 API 字段应遵守上述语义。

## Automation Boundary

未来自动化通过新增独立对象演进，不把现有信号直接当作订单：

```text
MarketObservation
-> SignalObservation
-> Candidate
-> TradePlan
-> ExecutionIntent
-> Order
-> Fill
-> Position
```

当前只实现到条件化 `TradePlan`。`ExecutionIntent`、`Order`、`Fill` 和真实 `Position` 属于未来能力。当前代码不得把这些概念合并为一个布尔信号。

## Success Criteria

当前阶段优先衡量：

- 用户能否快速找到值得进一步查看的候选。
- 用户能否理解候选为何出现、缺少什么确认、何时失效。
- 单票页面能否同时提供最新行情和不被盘中数据污染的正式信号。
- 相同数据和策略版本能否复现相同结果。
- 日常查询是否稳定、快速，并避免扫描全部历史文件。

不以候选数量、信号数量或界面功能数量作为主要成功指标。
